# メモ: NPU で動かすときの用途の検討

2026-10-25〜28 の議論のメモ。材料は [phase4-results.md](phase4-results.md) の 4 節 (NPU PC での確認)。
結論として、**通知・メール・チャットのトリアージを常駐で行う**ことにした。
アイデアの中身は [triage.md](triage.md) に書いた。

## 1. NPU の性能の整理

| 項目 | 値 |
|---|---|
| 1 回の推論 | 約 0.8 秒 (エンドツーエンド)。系列長が 128 でも 512 でもほとんど変わらない |
| 1 回で扱える量 | 状態 383 トークン + 質問 5〜8 問 |
| 処理量 | 約 1 回/秒 (1 時間に約 3,600 回、1 日に約 8.6 万回) |
| 速くする手段 | バッチ (B≥4) と系列長 (160〜480、512 超) はハングするので使えない |
| 内蔵 GPU との比較 | 内蔵 GPU が 6〜7 倍速い (約 125〜215 ms)。系列長も 1,024 まで伸びる |
| 安定性 | ハングすると、プロセスを起動し直すまで戻らない |
| 起動 | 初回のコンパイルは 35〜65 秒、キャッシュがあれば 4.5 秒 |

- 測った軸 (速さ、長さ、バッチ) では、どれも内蔵 GPU のほうが上
- NPU を選ぶ理由として残るのは、**電力が小さいこと**と、**CPU や GPU を空けておけること**。
  ただし、どちらもまだ測っていない

## 2. 0.6 秒の固定オーバーヘッドへの疑問

phase4-results.md の 4.4 は、長さによらない約 0.6 秒が支配的なので、小さいモデルに蒸留しても NPU では速くならない、
と結論している。ただ、この数字は計算量から見て大きすぎる。

- mDeBERTa のエンコーダは約 8,600 万パラメータで、L=512 の 1 回はおよそ 100 GFLOP 前後。
  Core Ultra の NPU なら数十 ms で終わるはずの量
- 長さによらない処理として目立つのは、埋め込みの表 (語彙 約 25 万 × 768 × FP16 ≒ 384 MB)。
  推論のたびに NPU 側でこの表を Gather するために転送しているなら、0.4〜0.6 秒は説明がつく (**仮説。未確認**)
- 相対位置の計算 (`Log` / `Ceiling` / `GatherElements`) が NPU の効率の悪いユニットで動いている可能性もある

切り分けは `benchmark_app -m model.xml -d NPU -pc` の層ごとの時間でできる。埋め込みが原因なら、
埋め込みの参照を CPU で行って IR を `inputs_embeds` から始めるか、語彙 (日本語と英語) に表を絞る。

## 3. いまの性能 (約 1 秒/回) で向く用途と向かない用途

向く条件は、**非同期・常駐・短いテキスト・観点が多い・データを外に出したくない**こと。

| 用途 | 内容 |
|---|---|
| 通知・メール・チャットのトリアージ | 受信したものを状態にして、返信が要るか・急ぎか・カテゴリを 1 回で判定する。1 日数百件なら処理量の 1% も使わない (**採用**) |
| ローカル LLM の前段のルーターとガード | LLM は GPU、NPU は「重いモデルに回すか」「個人情報を含むか」を判定する。ハードウェアを奪い合わない (System One + System Two) |
| 教師ラベル付けの前のふるい | 大量の状態を夜間に判定し、confidence が低いものだけを Claude Code に送る。確率が較正されているので成り立つ |
| 作業ログ・日報・ファイル名などのタグ付け | 急がないバックグラウンドの処理。長い文書はヘッダを付けたチャンクに分ける |
| クリップボードや送信前の文章のチェック | 1 秒の待ちが気にならない場面に限る |

向かない用途:

- 長い入力を同期のゲートで止める用途
- 100 ms 級の応答が要る対話的な用途 (入力の補完など)。内蔵 GPU なら届く
- 大量の一括処理 (内蔵 GPU や開発 PC の GPU のほうが一桁速い)
- 1 回で 383 トークンを超える文脈が要る判定

## 4. 推論の時間が半分になった場合

| | いま | IR だけ半分 | エンドツーエンドで半分 |
|---|---|---|---|
| 1 回の推論 | 約 0.8 秒 | 約 0.53 秒 | 約 0.4 秒 |
| 処理量 | 約 1.2 回/秒 | 約 1.9 回/秒 | 約 2.5 回/秒 (1 日に約 20 万回) |
| 1,000 トークンの文書を 5 観点で見る (3 回) | 約 2.4 秒 | 約 1.6 秒 | 約 1.2 秒 |

エンドツーエンドの 803 ms のうち約 250 ms は Python とトークナイザの側なので、IR だけを速くしても 0.53 秒で止まる。

人が待てる時間の境目 (約 0.1 秒: 遅れを感じない / 約 0.5 秒: 操作への反応として許される / 約 1 秒: 作業は途切れない) のうち、
約 0.5 秒をまたぐ。新しく入るのは、**利用者の操作のたびに同期で判定する用途**:

- 送信や確定の直前の同期チェック (機密情報、宛先と内容の食い違い、語調)
- 入力が止まったときのライブフィードバック (止まってから 0.5 秒 + 推論 0.4 秒 ≒ 0.9 秒で表示)
- エージェントのツール呼び出しごとの判定 (Claude Code の PreToolUse フックなど)
- ローカル LLM のストリーミング出力を文ごとに判定する (生成の監視)
- 会議の書き起こしをリアルタイムで判定する (観点を増やす余裕ができる)
- 1,000 トークン程度の文書を約 1 秒でゲートする (保存や提出のタイミングに限る)

半分でも、0.1 秒級の用途と大量の一括処理には向かない。同期で使うなら、ハングに備えたタイムアウトと
そのときの方針 (通す / 止める / 内蔵 GPU で判定し直す) が要る。

## 5. 次に確かめること (安い順)

1. NPU ドライバの更新 (phase4-results.md の 4.6)
2. `benchmark_app -pc` で層ごとの時間を出し、0.6 秒の内訳を調べる
3. 電力と同時実行の測定。`bench` 中のパッケージ電力と、内蔵 GPU で LLM などを動かしながら判定したときの互いの遅れ。
   NPU が勝たなければ、既定のデバイスは内蔵 GPU にする
