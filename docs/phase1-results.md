# フェーズ 1 の結果 (パック入力とモデル)

実施: 2026-10-03。環境はフェーズ 0-a と同じ (ワークショップ `gpu`、GTX 1660 Ti、torch 2.11.0+cu128、
transformers 5.18.0、openvino 2026.4.1)。モデルは mDeBERTa (学習なし)。

## まとめ

- パック方式 (`--arch packed`) が torch (GPU / CPU) で動く。`decide` と `bench` で使える
- 質問同士の独立はテストで保証した (1 つだけ渡したときと一緒に渡したときで一致、順番を変えても一致)
- **マーカーの位置番号は 0 (`marker_position: cls`) を採用**。学習なしでもペア方式と 92〜97% 同じ判定になる。
  プランの「状態のすぐ後ろ」(`after`) だと 57〜63% まで落ちる
- choice は、指示を共有する形 (`shared`) でもテンプレート (`{option}`) があればペア方式と 95% 一致する。既定は `shared`
- 速さは GPU で 1 件 (noul 3 問 + 5 択) が **195 ms → 19 ms**
- パック方式のグラフは OpenVINO に変換でき、CPU で torch と一致した (NPU は未確認)

## 1. 実装

| ファイル | 内容 |
|---|---|
| `packing.py` | 状態と質問を 1 本の系列に詰める (`pack`)、マーカーごとのロジットを質問ごとに戻す (`unpack`) |
| `packed_model.py` | `PackedDecider`。グラフ内でマスクと相対位置を作り、マーカー位置から判断ロジットを読む |
| `torch_backend.py` | `TorchPackedScorer` (パック方式の torch 推論) |
| `scoring.py` | `S1Config` にパック方式の設定を追加。`DEFAULT_BASE_MODEL` を mDeBERTa に変更 |
| `decide.py` | `Decider` が `score_questions` を持つ scorer (パック方式) も受け付ける。温度は bool と choice で別 |
| `cli.py` | `decide` / `bench` に `--arch pair\|packed` を追加 |

系列の形 (既定の設定):

```
[CLS] 状態 [SEP] | [Q] 質問1 [SEP] | choice の指示 [O] 選択肢A… [SEP] [O] 選択肢B… [SEP] | PAD
位置  0 … S-1       0   S …            S …           0   S+I …         0   S+I …
```

プランから変えた点:

- **入力テンソルは 5 個**: `input_ids`、`question_ids`、`option_ids`、`positions`、`marker_index`。
  選択肢が「親の質問」を見るための情報が要るので、`segment_ids` を質問番号と選択肢番号の 2 本に分けた。
  役割 (状態 / 質問 / 選択肢) はこの 2 本からグラフ内で求める
- **マーカーの位置番号は 0**: ペア方式の `[CLS]` と同じ見え方になる (2 節)
- **choice の指示にはマーカーを付けない**: 読むのは選択肢のマーカーだけなので省いた
- **`{option}` の扱い**: `{option}` より前を共有の指示にし、選択肢の側に `{option}` 以降をつなげる。
  例: 「この問い合わせは{option}に関するものだ。」→ 指示「この問い合わせは」、選択肢「配送に関するものだ。」
- **状態の長さは `max_state_tokens` (既定 384) で固定**: 他の質問の量で状態の切り詰め方が変わると、
  質問同士が独立でなくなるため。質問に使えるのは残り (最大長 512 なら 128 トークン以上) で、
  入りきらない質問や選択肢は次の回の推論に回す
- **`s1.json`**: `temperature` を `temperature_bool` / `temperature_choice` に分けた。
  以前の形式 (`temperature` が 1 つ) も読める

実装で分かったこと:

- transformers の DeBERTa-v2 は、サンプルごとに違う相対位置を `[B, L, L]` で渡すとバッチ 2 以上で動かない
  (内部で `squeeze(0)` してから `[B × ヘッド数, L, L]` に広げるため)。`[1, B × ヘッド数, L, L]` の形で渡して回避した。
  バッチ推論が 1 件ずつの結果と一致することはテストで確認済み (フェーズ 3 の学習で必要)
- エンコーダは渡された相対位置をバケットに変換しないので、`make_log_bucket_position` を自分で通している。
  状態の `[CLS]` から読んだ値が、状態だけを元のモデルに通した値と一致することをテストで確認した

## 2. zero-shot でのペア方式との一致

`scripts/phase1/zero_shot_agreement.py`。評価セットはフェーズ 0 と同じ `ja_eval.yaml`
(noul 60 問、topic 5 択 20 問)。1 件につき noul 3 問 + topic を 1 回で推論する。
規模が小さいので、正解率の ±6 ポイント程度の差はノイズとみなす。

ペア方式の正解率: noul 平叙文 0.667 / 疑問文 0.717、topic 平叙文 0.750 / 疑問文 0.750 / 疑問文+選択肢 0.400。

**noul** (choice の詰め方には影響されない)

| マーカー | 文 | 正解率 | ペアと同じ判定 | 確率の差の平均 | z の相関 |
|---|---|---|---|---|---|
| `cls` | 平叙文 | 0.633 | **0.967** | 0.086 | 0.913 |
| `cls` | 疑問文 | 0.767 | **0.917** | 0.105 | 0.873 |
| `after` | 平叙文 | 0.600 | 0.633 | 0.284 | 0.666 |
| `after` | 疑問文 | 0.550 | 0.567 | 0.334 | 0.445 |

**topic** (正解率 / ペアと同じ選択)

| マーカー | 詰め方 | 平叙文 | 疑問文 | 疑問文+選択肢 |
|---|---|---|---|---|
| `cls` | `shared` | 0.700 / **0.950** | 0.700 / 0.950 | 0.550 / 0.650 |
| `cls` | `expanded` | 0.750 / **1.000** | 0.700 / 0.950 | 0.450 / 0.550 |
| `after` | `shared` | 0.550 / 0.750 | 0.650 / 0.850 | 0.450 / 0.500 |
| `after` | `expanded` | 0.600 / 0.800 | 0.600 / 0.800 | 0.500 / 0.600 |

- `cls` は学習なしでペア方式にかなり近い。「状態が質問を見ない」ことによる差は、確率で平均 0.09〜0.10
- `after` は NLI ヘッドが学習した `[CLS]` (位置 0) と見え方が違うので大きく崩れる。既定を `cls` にした
- `shared` と `expanded` の差は 20 問中 1 問で、ノイズの範囲。トークンが少なく済む `shared` を既定にした
- 「疑問文+選択肢」(テンプレートなし) はペア方式でも 0.400 なので、一致率が低くても問題にしない。
  この形の扱いはフェーズ 0 の結論どおり、フェーズ 2〜3 の学習かフェーズ 6 の仮説文の作り方で対応する

**フェーズ 3 の基準**: `cls` + `shared` で、noul の判定の一致 0.92〜0.97、topic の選択の一致 0.95。
蒸留でこれをどこまで上げられるかを見る。

## 3. 速さ

1 件 = noul 3 問 + 5 択 (ペア方式では 8 ペア)。p50。

| 方式 | バックエンド | 形状 | p50 |
|---|---|---|---|
| ペア | torch / cuda | 8 × 256 | 195 ms |
| パック (`shared`) | torch / cuda | 1 × 128 | 19 ms |
| パック (`expanded`) | torch / cuda | 1 × 128 | 20 ms |

`examples/review.yaml` (bool 2 問 + 3 択) の `bench`: ペア 122 ms、パック 19 ms (torch / cuda)。
回答はほぼ同じ (`positive` 0.9997 → 0.9995、`recommends` 0.991 → 0.968、`genre` = a novel 0.985 → 0.987)。

速くなる理由は、推論が 1 回で済むことと、系列が短い長さ (128) に収まること。

## 4. OpenVINO への変換 (フェーズ 4 の先取りの確認)

`PackedDecider` を `ov.convert_model` で変換し、1 × 128 に固定して CPU で動かした
(確認用の使い捨てスクリプト。`export` への組み込みはフェーズ 4)。

- 変換は通り、出力は torch と一致 (差の最大 1.4e-5)
- OpenVINO CPU で 1 × 128 が約 47 ms (参考: ペア方式の 8 × 256 は 1,253 ms)
- グラフに `If` が 1 種類入っている。NPU でコンパイルできるかはフェーズ 0-b / 4 で確認する

## 残っていること

- NPU での確認 (フェーズ 0-b)。mDeBERTa が NPU で動かなければ、`packed_model.py` は DeBERTa 固有なので作り直しになる
- 役割埋め込み (`role_embeddings`) の保存と読み込み。学習前は 0 なので、今は保存していない (フェーズ 3)
- パック方式の `export` と OpenVINO バックエンド (フェーズ 4)
