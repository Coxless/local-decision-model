# アイデア: 通知・メール・チャットのトリアージを常駐で行う

作成: 2026-10-28。状態: アイデア (未着手)。用途を選んだ経緯は [npu-use-cases.md](npu-use-cases.md)。

NPU PC にサーバー (`serve`) を常駐させ、届いた通知・メール・チャットを 1 件ずつ判定して、
「いま見るべきもの」と「後でよいもの」に振り分ける。判定は手元の PC の中だけで行い、本文を外に送らない。

## 1. なぜこの用途か

| 条件 | トリアージでは |
|---|---|
| 非同期でよい | 届いてから 1 秒後に判定が出ても困らない。いまの NPU (約 0.8 秒/回) で足りる |
| 短いテキスト | 件名・送信者・本文の先頭で、状態 383 トークンにおおむね収まる |
| 観点が多い | 返信の要否・急ぎか・カテゴリなどを、パック方式の 1 回の推論でまとめて答えられる |
| 処理量が小さい | 1 日に数百〜数千件。NPU の処理量 (1 日に約 8.6 万回) の数 % |
| データを外に出したくない | 個人のメールやチャットをクラウドに送らずに済む |
| GPU を空けておきたい | 常駐の処理を NPU に寄せれば、GPU と CPU を他の作業に使える |

文字列を生成しないので、出力は必ず決めた型 (noul / choice) に収まり、アプリ側で扱いやすい。
確率が較正されているので、しきい値で「自動で振り分ける」「人に聞く」を分けられる。

## 2. 全体の構成

```
取り込み (メール / チャット / OS の通知)
   │  1 件ずつ、状態のテキストに整える
   ▼
キュー (届いた順。急ぐものはない)
   │
   ▼
サーバー (POST /v1/systemone、NPU)  ──  ハングしたら起動し直す / 内蔵 GPU に切り替える
   │  回答 (noul の確率、choice の確率と confidence)
   ▼
振り分け (しきい値) → 通知する / まとめて後で見せる / 何もしない
   │
   ▼
記録 (判定と、利用者が実際にどうしたか。精度の確認と学習データに使う)
```

- サーバーは今あるもの (System One と互換の API) をそのまま使う。トリアージの側は HTTP で呼ぶだけの別のプログラムにする
- 取り込みは、ソースごとに小さなアダプタを書く。最初は 1 つのソースだけにする (5 節)

## 3. 状態と質問

### 状態

状態は「誰から・どこで・何について」が先頭に来るように整える。383 トークンを超える分は切り詰められるので、
大事な情報ほど前に置く。

```
チャネル: メール
送信者: 山田 (取引先 A 社)
宛先: 自分 (To) / CC 3 名
件名: 来週の打ち合わせの日程
本文:
お世話になっております。来週の打ち合わせですが、…
```

- サーバーは JSON の状態も受け付けるが、精度は未検証なので、まずは上のような平文にする
- 長いスレッドは、最新のメッセージと、件名・送信者のヘッダだけを入れる (引用部分は削る)

### 質問 (案)

1 回の推論に収まる 5〜8 問に絞る。指示は平叙文で書く (疑問文での精度は未確認。plan.md の未決事項 6)。

| 質問名 | 型 | 指示 / 選択肢 |
|---|---|---|
| `needs_reply` | noul | 受信者が返信する必要がある。 |
| `request_to_me` | noul | 受信者に何かを依頼している。 |
| `has_deadline` | noul | 期限や日時の指定がある。 |
| `automated` | noul | 自動送信の通知や配信メールである。 |
| `priority` | choice | このメッセージは {option} 対応すべきだ。 — すぐに / 今日中に / 今週中に / 対応は不要 |
| `category` | choice | このメッセージの種類は {option} だ。 — 仕事の連絡 / 個人的な連絡 / 請求や支払い / お知らせ / 広告 |

- 水準 (優先度) は本来 score 型だが、score は未対応なので choice にする
- 質問はアプリの側で持ち、利用者が足したり変えたりできるようにする。ただし学習にない質問の精度は未確認 (plan.md の未決事項 8)

### 振り分けの方針

- 自動でやるのは「通知する / 後でまとめる」の振り分けだけ。削除やアーカイブ、返信はしない
- しきい値を超えないもの、choice の confidence が低いものは「未判定」として、利用者に見せる側に倒す
- しきい値は記録 (2 節) を見て決める

## 4. 課題とリスク

1. **分野が違う**: 学習データの状態は「顧客からの問い合わせ」(plan.md の未決事項 1)。
   個人のメールやチャット、OS の通知は学習にない分野なので、まず今のモデルでどれだけ当たるかを測る
2. **学習データとプライバシー**: 教師は Claude Code だが、自分のメールを教師に送ると「外に出さない」という前提が崩れる。
   学習データは、`scripts/phase2/generate_states.py` と同じように Claude Code に書かせた架空のメッセージで作る。
   実際のメッセージは、手元での評価 (判定と利用者の行動の比較) にだけ使う
3. **NPU のハング**: 系列長 160〜480 で `ZE_RESULT_ERROR_DEVICE_LOST` になり、起動し直すまで戻らない。
   `lengths` は `[512]` だけにし、サーバーの側でハングを検知して起動し直す (または内蔵 GPU に切り替える) 仕組みが要る
4. **NPU を使う理由の裏付け**: 速さでは内蔵 GPU が上。電力と、他の作業と同時に動かしたときの影響を測るまでは、
   内蔵 GPU で動かす選択肢も残しておく (npu-use-cases.md の 5 節)
5. **常駐の方法**: 手動起動・スタートアップ・Windows サービスのどれにするかは未決 (plan.md の未決事項 5)

## 5. 進め方 (案)

1. **質問セットと評価用のデータを作る**: 架空のメッセージ (メール、チャット、通知) を Claude Code に書かせ、
   3 節の質問で評価セットを作る。今のモデルで正解率と ECE を測る
2. **読むだけで動かす**: ソースを 1 つ選び、届いたものを判定して記録するだけのプログラムを作る。振り分けはまだしない。
   判定と、利用者が実際にどうしたか (返信したか、すぐ開いたか) を比べる
3. **学習する**: 1. と 2. の結果が足りなければ、架空のメッセージで学習データを作ってファインチューニングする
4. **常駐させて振り分ける**: NPU PC で `serve` と取り込みを常駐させ、しきい値で振り分ける。ハングからの自動復帰を入れる
